# Decisions

| ID | Date | Decision | Why |
|---|---|---|---|
| D-001 | 2026-09-26 | Clone SaaS foundation v1.0.1 rather than build standalone (Shane). A product = an org. | Sign-in for the dashboard, cron for `rollups:run`, CI and prod-build e2e come ready, and Askboard gets a host. Cost: we use tenancy as a single org. |
| D-002 | 2026-09-26 | Stack and port: Next 16 + Prisma 7 + local Postgres 17, port 4500. | House stack; 4500 was the next free hundred. |
| D-003 | 2026-09-26 | `/ingest` authenticates with a per-org write key (`Authorization: Bearer pk_…`), stored as a sha256 hash. | A public write endpoint needs a credential; hashing follows INV-07. No session, no rate limit (it would fight the load target). |
| D-004 | 2026-09-26 | Envelope `{ "events": [...] }`, 1–500 rows, body ≤ 1MB. Whole-request problems → 4xx; per-row problems → 200 with `rejected[{index, reason}]` and a `DeadLetterEvent` row. | PRD P0-1: valid rows in a bad batch still land. |
| D-005 | 2026-09-26 | Timestamps: ISO 8601 with offset. Future → clamped to `receivedAt`. Older than 365 days → dead-lettered. | PRD build note (clamp future, accept late); the 365-day floor keeps a 1970 clock from polluting rollups. |
| D-006 | 2026-09-26 | One `INSERT … SELECT FROM unnest(arrays) ON CONFLICT DO NOTHING` per batch. `accepted` = rows inserted, `duplicates` = valid − inserted. | One round trip per batch whatever its size; dedupe is the index's job, including repeats inside one batch. |
| D-007 | 2026-09-26 | `Event` carries only the pk and the dedupe index for now. Query indexes are added in Phases 2–3 with a measurement. | Every index taxes the write path; add them when a query needs them. |
| D-008 | 2026-09-26 | Late events are found by `receivedAt > watermark` (Phase 2), so ingest does no dirty-window bookkeeping. | Keeps the write path to one statement. |
| D-009 | 2026-09-26 | Rollup days are UTC. A dirty day is rebuilt with DELETE + INSERT … SELECT in the org's transaction; the watermark (max `receivedAt` seen) advances in the same transaction, and its row lock serializes concurrent runs. | Recompute, not increment, makes a re-run and a replayed batch exact by construction. Per-org timezones are out of scope (PRD). |
| D-010 | 2026-09-26 | Each run re-scans from watermark − 1 minute. | `receivedAt` is stamped by the app before the insert commits, so a slow commit or a skewed app clock can make a row visible behind the watermark. Overlap costs a re-run of the latest day, never a double count. Ceiling: skew beyond 1 minute. |
| D-011 | 2026-09-26 | Added `Event(orgId, ts)` and `Event(orgId, receivedAt)`. Write cost unmeasurable at 100k (README → Performance). Re-measured over HTTP at 1M+ rows (2026-09-28, `load:run`): no throughput cost at 40k ev/s, worse p95 near saturation. **Kept**: the reads need them and the target is 1k ev/s. | The dirty-day scan needs `receivedAt`; the per-day rebuild needs `ts` or every dirty day seq-scans `Event`. |
| D-012 | 2026-09-26 | `RegisteredProperty.eventName` null = every event; unique `NULLS NOT DISTINCT`. Property values are `properties->>prop` truncated to 200 chars; missing/null values are not rolled up. Registering a prop affects days rebuilt afterwards (no backfill yet). | A btree key over an 8KB value would fail the whole run; truncation keeps one bad property from blocking rollups. Backfill waits for the P1 property-management UI. |
| D-013 | 2026-09-26 | Rollups ride the existing hourly `/api/cron`. | PRD targets fresh within 5 minutes: a known gap until a 5-minute schedule is chosen at deploy (the job is idempotent, so any cadence is safe). |
| D-014 | 2026-09-26 | `rollups:verify` skips days holding an event newer than the watermark. | Those days are pending, not drifted; counting them would make verify fail between every ingest and the next run. |
| D-015 | 2026-09-26 | Retention reads a new rollup, `RollupUserDay(orgId, day, eventName, userId)`, rebuilt with each dirty day. `rollups:verify` checks its rows per (day, event) equal raw uniques. | Reads come from rollups, and `RollupDaily` has no per-user activity. Day grain (not week) keeps daily retention possible; eventName keeps "return on a specific event" possible (P0-4). |
| D-016 | 2026-09-26 | Funnel semantics: entry = any step-1 event with ts in [from, to); each next step = the user's earliest match strictly after the previous one by (ts, id), within the window of the entry (inclusive); later steps may fall past `to`; a user's level is the best over all their entries, counted once. 2–10 steps. | Greedy earliest-next is optimal for a fixed entry; best-over-entries lets re-entry convert (as Amplitude/ClickHouse `windowFunnel`). (ts, id) breaks timestamp ties by arrival and stops a repeated step reusing one event. |
| D-017 | 2026-09-26 | Added `Event(orgId, userId, eventName, ts, id)` for the funnel's next-step seek. No per-user-first-touch table. | 1M events: funnel without it >9.5 min (cancelled), with it 256–496ms (README → Performance). PRD sanctions the first-touch table only above 2s. |
| D-018 | 2026-09-26 | Retention: cohort = UTC Monday-start week of the user's first event over all time; periods W+1…W+8; a week not yet started is null (the current, partial week counts); cohorts are picked by week start in [from, to) and weeks with no new users are omitted. | First-seen over all time makes membership independent of the query range; only a late, earlier-stamped event moves a user, which is correct. |
| D-019 | 2026-09-28 | The dashboard gets a full design system (tokens, type, chart palette and mark specs, components, light/dark), published as a design-system artifact, **before** any styling lands. Order: finish 4c `load:run`, then 4d design system, then 4e apply it. | The dashboard is the portfolio face and the capstone demo (load run into a live dashboard); it shipped in 4b as unstyled HTML with the template title. Chosen over styling ad hoc in one pass. |
| D-020 | 2026-09-28 | Design system "Pulseboard" published (https://claude.ai/artifact/7D65arDGpQEq88bpyT6eWa): green-grey neutrals, teal `accent` for UI only, IBM Plex (Sans Condensed display, Sans UI, Mono data), borders not shadows, no motion. Charts never use `accent`: `series-1..3` (teal/orange/blue) pass the dataviz validator all-pairs in both themes; retention uses fixed buckets `heat-1..6` (<5, 10, 20, 35, 50, 50+%) with the value printed in every cell. Freshness pill: good ≤ 90 min since `RollupWatermark.ranAt`, warn older, critical never. Components are CSS class recipes (`.pb-*`), not a React bundle; hover is native SVG `<title>`, no client JS. | The app has no CSS at all and is server components, so class recipes drop straight into one `globals.css`. Fixed heat buckets keep two date ranges comparable; a 90-min threshold is the hourly cron (D-013) plus slack. Every text pair measured ≥ 4.5:1 in both themes. |
| D-021 | 2026-09-28 | Applied the Pulseboard design system (D-020) to `/o/[org]`: tokens + component CSS in `src/app/globals.css` (no Tailwind, matches the app), three Plex families via `next/font/google` with distinct CSS var names so they don't collide with the token names they feed, `OrgNav` split into a client component so `aria-current` reflects the real pathname (the server layout is shared across every `/o/[org]/*` route). Fixed 2 real bugs found eyeballing against the seeded `demo` org: TrendChart's y-axis gridlines were `mx/3` of an arbitrary ceiling, producing repeating decimals (`6.666666666666667k`) that overflowed the page's left edge — replaced with a nice step × 1/2/3; FunnelChart's row grid gave the caption column `auto` width, which claimed the full unwrapped caption before the bar's `1fr` track got any space, collapsing it to invisible under ~400px — capped the caption column. Both fixes pushed back to the design-system artifact (bundle.css, TrendChart's README) so future consumers don't hit them. | `next/font`'s own CSS custom property and the design system's token of the same name would otherwise race on cascade order depending on Next's internal stylesheet injection order; renaming one side removes the ambiguity entirely instead of relying on load order. |
| D-022 | 2026-09-28 | **Cost review at closure.** Baseline: nothing deployed, so **$0** (no `.vercel` link, no Vercel project, no Neon project; checked with `vercel project ls` and `neonctl projects list`). GitHub Actions: 17 CI runs since 2026-09-01 at ~3 min each (~50–100 min of the private-repo 2,000 free min/month). Line by line: **Vercel auto-deploy per push → off** (no project; if ever deployed, `ignoreCommand` is already in `vercel.json`, and turn auto-deploy off unless a live demo needs it). **`/api/cron` hourly → slow to daily if deployed** (`"schedule": "0 5 * * *"`); restore `"0 * * * *"` (or `*/5` for the PRD's freshness, D-013) only when real events arrive. The freshness pill (D-020) will read warn on a daily cadence; that is honest. **Neon → not created**; if deployed, `suspend_timeout` default (5 min) and `?connection_limit=10`, and measure the ~1M-event seed's size (`SELECT pg_size_pretty(pg_database_size(current_database()))`) against the plan's storage limit before seeding it there. **Resend / Stripe → off** (template modules, keys empty, Stripe test mode only). **LLM calls → none.** **CI on push → keep** (the only recurring spend, well under the free allowance). | Demo/learning project defaults to off or daily (conventions → *Cost review at closure*). The restore values are written here so turning anything back on is one edit, not a re-derivation. |
| D-023 | 2026-09-29 | The scan starts at `min(watermark, previous run's start − OVERLAP_MS)`, and `ranAt` is now stamped when a run **starts** (before its scan), not when it ends. Refines D-010. | A row the previous run missed committed after that run started, so under D-010's same 60s ceiling its `receivedAt` is no earlier than start − 60s. Before this, after `seed:generate` every idle run re-scanned the load's last minute, whose `ts` spans 90 days, and rebuilt 91 days each time (26s quiet, 530s under load); now one follow-up run does it, then idle runs rebuild 0 days. A start-time `ranAt` makes the freshness pill (D-020) read up to one run's duration older, which is the conservative direction. |
| D-024 | 2026-10-13 | Freshness pill warns past **26 h**, not 90 min. `FRESH_WARN_MS` moves to `src/lib/dashboard.ts` as the one shared constant, and `tests/unit/freshness.test.ts` reads the `/api/cron` schedule from `vercel.json` and fails if the threshold is not between one and two cron intervals. Refines D-013 / D-020's 90-min threshold. | The cron went daily (`0 6 * * *`, 3b8b080). With a 90-min threshold every dashboard read "stale" for about 22 h a day, so the warning carried no signal. **Restore:** if the schedule goes back to `0 * * * *`, the test fails until `FRESH_WARN_MS` is set back to `90 * 60 * 1000`. |
| D-025 | 2026-11-05 | **`/ingest` authenticates with the template's `apikeys` module (v1.6.0 M13), superseding D-003's key format and its no-rate-limit rule.** Keys are `api_…` ApiKeys with scope `ingest`, issued at `/o/[org]/settings/apikeys` or by `npm run key:create -- <orgSlug>` (owned by the org's first owner). The route calls `requireApiKey(req, 'ingest')`: 401 / 403 / 429 are now `application/problem+json`; the body errors (400 / 413) keep `{ error }`. `ingest` allows **3,000 requests per key per minute**. Migration `20261109000000_pulseboard_drop_write_key` drops `WriteKey` and copies no rows. `Org.events` became `Org.pbEvents` (core took `events` for `OrgEvent`). `apikeys` is listed in `src/app/required-modules.ts`, so `foundation:check-modules` leaves it in place. | Owner decisions 2026-11-05: (1) reissue, because the `pk_…` keys could never pass `resolveKey`'s `api_` prefix check and Pulseboard is not deployed, so only local dev keys are lost; (2) 3,000 is 2.5x `load:run`'s target of 1,000 ev/s in 50-event batches (1,200 requests a minute). **Restore:** none. A larger load target raises `ingest.perMinute` in `src/app/api-scopes.ts`. |
| D-026 | 2026-11-05 | Org export (v1.6.0 M11, INV-34): Pulseboard exports `Event`, `DeadLetterEvent` and `RegisteredProperty`, and skips `RollupDaily`, `RollupDailyProp`, `RollupUserDay` and `RollupWatermark` with a reason (`src/app/export-hooks.ts`). | The raw events are what an org sent and owns. The rollups are derived from them and `runRollups` rebuilds them. `Event` loads in one query under the export's 500 MB guard (`ponytail:`); page it if an org ever hits the guard. |
| D-027 | 2026-11-05 | RLS (v1.6.0 M9): `20261109000001_rls_policies_pulseboard` (from `npm run rls:policies`, 26 tables) adds policies for Pulseboard's 7 tables. **Pulseboard still runs RLS off.** Under `RLS_MODE=enforce`, ingest, rollups, the dashboard, funnels and retention fail, because they query through `db` rather than `withOrg`/`asSystem`. INV-29 also fails on Pulseboard's tables, because the template's fixture seeds no clone rows. INV-30 to INV-34 pass. | Open for the owner: port Pulseboard's queries to `withOrg` (rollups and cron through `asSystem` plus `cross-org.ts`) and get a clone fixture hook into the template's INV-29, or drop CI's `enforce` leg for Pulseboard. |
